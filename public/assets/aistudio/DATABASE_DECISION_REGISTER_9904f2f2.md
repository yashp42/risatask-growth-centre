## 2. Schema & Source-Document Ambiguities (`AMB-*`)

| Ambiguity ID | Conflict / Gap Found | Source Evidence | Impacted SQL Objects | Decision Taken in Stage 1B (Reversible Before Live Load) |
|---|---|---|---|---|
| `AMB-TEAM-AUTH-JOIN` | `01_conceptual_data_model.md` §4A defines `TEAM_MEMBER` with `email UK` ("Login identity") and no `auth_user_id`; `10_technical_architecture_handoff.md` §3 requires joining `role_assignment` to `team_member` by `auth user id`. | `01_cdm §4A` vs `10_tech §3` vs `server/auth.ts` | `public.team_member` (`email`, `auth_user_id`, `is_active`) | Included both `email TEXT UNIQUE` and nullable `auth_user_id UUID UNIQUE` (forbidden for `historical_synthetic` rows), plus `is_active BOOLEAN`. Approve primary join invariant (`auth_user_id` bound on first user provisioning). |
| `AMB-TASK-PROVENANCE` | `01_conceptual_data_model.md` §4E `TASK` header specifies `Allowed record classes: live, simulated` while Provenance text says `Live only`. Additionally, Constraints require `done requires completed_at`, yet `completed_at` was omitted from the `TASK` attribute table. | `01_cdm §4E` lines 1439, 1456, 1458 | `public.task` (`record_class`, `completed_at`) | Allowed `record_class IN ('live', 'simulated')` matching the entity header and Stage 1B demo needs, and added `completed_at TIMESTAMPTZ` with `CHECK (status <> 'done' OR completed_at IS NOT NULL)`. |
| `AMB-SUPPORT-TYPE-2025` | `05_metric_dictionary.csv` computes M-03/M-04 from `OPPORTUNITY.support_type` (`cash / in_kind / mixed`), whereas 2026 commercial contracts split cash vs in-kind at `CONTRACT_LINE.consideration_type` (`cash / in_kind`). | `05_metric_dictionary.csv` M-03/M-04 vs `01_cdm §4C` | `public.opportunity.support_type`, `public.contract_line.consideration_type` | Preserved both columns distinctly without collapsing or inferring one from the other. Stage 2 metric SQL functions (`metrics.m_03`, `m_04`) must branch cleanly by `record_class` (`historical_synthetic` uses `opportunity.support_type`; `live`/`simulated` uses `contract_line.consideration_type`). |
| `AMB-TIME-LOG-NAME` | `01_conceptual_data_model.md` §4E names the entity `TIME_LOG` (`time_log_id`), while `10_technical_architecture_handoff.md` §2.1 refers to `hours_log`. | `01_cdm §4E` vs `10_tech §2.1` | `public.time_log` | Used canonical conceptual entity name `public.time_log` (preserving `time_log_id`). Documented `hours_log` as an informal alias only. |
| `AMB-RECEIPT-RECONCILE` | `01_conceptual_data_model.md` §4D marks `RECEIPT` versioning = `immutable`, while `reconciled boolean` transitions during bank statement reconciliation (`IN-10`). | `01_cdm §4D` vs `04_integration_requirements.md` IN-10 | `public.receipt`, `tg_protect_receipt_immutability()`, `public.reconcile_receipt()` | Enforced strict immutability on all monetary/identity/date attributes (`amount`, `sponsor_id`, `received_at`, `method`, `bank_reference`, `recorded_by`, `record_class`) while allowing one-way `reconciled: false -> true` solely inside `reconcile_receipt()`. |
| `AMB-INVOICE-IMMUTABLE` | `01_conceptual_data_model.md` §4D marks `INVOICE` versioning = `immutable` ("cancel with a credit note"), yet lists `status` enum `issued / cancelled (credit note) / settled`. | `01_cdm §4D` lines 1234, 1245, 1250 | `public.invoice`, `tg_protect_invoice_immutability()` | Locked all financial/identity fields (`invoice_no`, `contract_id`, `schedule_item_id`, `issued_at`, `amount`, `tax_amount`) unconditionally; allowed `status` transitions only under a controlled finance function flag (`app.finance_fn_active`), pending OD-15 decision on separate credit-note rows vs `status = 'cancelled'`. |
| `AMB-AI-TABLES` | `10_technical_architecture_handoff.md` §2.1 & §2.5 explicitly specify `ai_conversation` and `ai_message` tables (`GET /api/ai/conversations/:id`, last 10 turns), but `01_conceptual_data_model.md` §4G only defines `ai_query_log`, `ai_action`, and `audit_event`. | `10_tech §2.1 & §2.5` vs `01_cdm §4G` | `public.ai_conversation`, `public.ai_message`, `public.ai_query_log.conversation_id` | Provisioned `public.ai_conversation` and `public.ai_message` with standard provenance blocks and linked `ai_query_log.conversation_id` (nullable FK) so Stage 4 conversation memory works cleanly. |
| `AMB-METRIC-CSV-COLS` | `01_conceptual_data_model.md` §4F `METRIC_DEFINITION` omits several columns present in `05_metric_dictionary.csv` (`kpi_id`, `name`, `business_meaning`, `time_period`, `inclusion_exclusion`, `source_table_2025`, `source_table_future`, `unit`, `computable_2025`, `example_calculation`, `example_value_2025`). | `01_cdm §4F` vs `05_metric_dictionary.csv` | `public.metric_definition` | Included all canonical `01_cdm` columns plus all `05_metric_dictionary.csv` columns (and `definition_version`) so `04_reference_seed.sql` loads `05_metric_dictionary.csv` losslessly without modifying source CSV structure. |
| `AMB-AI-ACTION-TYPES` | `01_conceptual_data_model.md` §4G lists draft/example types (`create_task / log_interaction / create_campaign / draft_proposal ...`) while `10_technical_architecture_handoff.md` §2.5 & §3 strictly restrict first-release actions to 4 types: `create_task`, `log_interaction`, `log_meeting`, `upsert_sponsor_contact` ("Any other action type does not exist"). | `01_cdm §4G` vs `10_tech §2.5 & §3` | `public.ai_action.action_type` | Constrained `ai_action.action_type` strictly to the 4 approved first-release action types (`create_task`, `log_interaction`, `log_meeting`, `upsert_sponsor_contact`) to enforce Stage 1A/Stage 4 safety guarantees at DB level. |
| `AMB-VERSION-PK-PATTERN` | Full-state versioned reference/commercial entities (`kpi_definition`, `metric_definition`, `proposal`, `contract`, `referral`, `prospect_research`, `target_version`, `threshold_rule`, `role_assignment`, `knowledge_chunk`) use single business-ID PKs (e.g. `metric_id`, `contract_id`) in `01_cdm` while also carrying `version_no`, `valid_from`, `valid_to`, `superseded_by`. | `01_cdm §2` vs §4 tables | All 15 full-state versioned tables | Preserved exact canonical PK column names and self-referencing `superseded_by` FKs. Superseding a version creates a new row ID (e.g. `M-01@v2` or new UUID/ID) and closes `valid_to` on the prior row, or awaits explicit Stage 2 surrogate-PK approval if same business key must repeat across versions. |
